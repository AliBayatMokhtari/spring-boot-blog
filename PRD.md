# Product Requirements Document (PRD)

## Blog Management System

### 1. Overview

The Blog Management System is a web application that allows users to create and manage blog posts, interact with posts through likes and comments, and authenticate securely.

The system will have two main types of users:

- **Authenticated users** — can create, edit, and delete their own posts and interact with posts.
- **Unauthenticated users** — can browse published posts but cannot create posts, comment, or like posts.

The primary goal is to provide a simple but complete blogging platform that demonstrates user authentication, authorization, content management, and social interactions.

---

## 2. Goals

The system should allow users to:

1. Register and authenticate securely.
2. Create and manage their own blog posts.
3. Browse and read published blog posts.
4. Comment on blog posts.
5. Like and unlike blog posts.
6. Manage their own comments.
7. Ensure users can only modify resources they own.
8. Provide a clean API that can be consumed by a web or mobile frontend.

---

## 3. Out of Scope

The following features are intentionally excluded from the first version:

- Admin dashboard
- Post categories
- Tags
- Post drafts
- Image/file uploads
- Rich text editor
- Notifications
- Following users
- Private posts
- Social sharing
- Search
- Email verification
- Password reset via email
- Pagination optimization
- Content moderation

These can be introduced in future versions.

---

# 4. User Roles

## 4.1 Guest User

A guest user can:

- View published posts.
- View a single post.
- View comments on a post.
- View basic author information.

A guest user cannot:

- Create posts.
- Edit posts.
- Delete posts.
- Like posts.
- Comment on posts.

---

## 4.2 Authenticated User

An authenticated user can:

- Create posts.
- View posts.
- Edit their own posts.
- Delete their own posts.
- Like/unlike posts.
- Add comments.
- Edit their own comments.
- Delete their own comments.
- View their profile.

Users cannot modify posts or comments created by other users.

---

# 5. Authentication

## 5.1 Registration

Users should be able to create an account using:

- Name
- Email
- Password

### Requirements

- Email must be unique.
- Email must have a valid format.
- Password must satisfy minimum security requirements.
- Password must never be stored as plain text.
- The system must securely hash passwords before storing them.

### Example

```text
POST /api/auth/register
```

Request:

```json
{
  "name": "John Doe",
  "email": "john@example.com",
  "password": "password123"
}
```

---

## 5.2 Login

Users should be able to authenticate using their email and password.

```text
POST /api/auth/login
```

Successful authentication should return an authentication token.

Example:

```json
{
  "accessToken": "..."
}
```

The token will be required for protected operations.

---

## 5.3 Authentication Requirements

Protected endpoints must reject requests when:

- No authentication token is provided.
- The token is invalid.
- The token is expired.

Expected response:

```text
401 Unauthorized
```

# 6. Blog Posts

## 6.1 Post Structure

Each blog post should contain:

- ID
- Title
- Content
- Author
- Created date
- Updated date
- Like count
- Comment count

Example:

```json
{
  "id": 1,
  "title": "Introduction to System Design",
  "content": "System design is...",
  "author": {
    "id": 10,
    "name": "John Doe"
  },
  "likeCount": 12,
  "commentCount": 5,
  "createdAt": "2026-08-19T10:00:00Z",
  "updatedAt": "2026-08-19T10:30:00Z"
}
```

---

# 7. Create Post

Authenticated users can create a new blog post.

```text
POST /api/posts
```

Request:

```json
{
  "title": "Introduction to System Design",
  "content": "System design is..."
}
```

### Requirements

- User must be authenticated.
- Title is required.
- Content is required.
- The authenticated user becomes the post author.
- Creation date must be generated by the server.

---

# 8. Get Posts

Users can retrieve a list of published posts.

```text
GET /api/posts
```

The response should contain:

- Post ID
- Title
- Short content/summary
- Author
- Like count
- Comment count
- Creation date

The API should support pagination.

Example:

```text
GET /api/posts?page=1&limit=10
```

---

# 9. Get Single Post

Users can retrieve a specific post.

```text
GET /api/posts/{postId}
```

The response should contain:

- Full post content
- Author information
- Like count
- Comment count
- Creation/update dates
- Comments

---

# 10. Update Post

Authenticated users can update their own posts.

```text
PUT /api/posts/{postId}
```

Request:

```json
{
  "title": "Updated Title",
  "content": "Updated content..."
}
```

### Authorization Requirements

The user must be the owner of the post.

If the post belongs to another user:

```text
403 Forbidden
```

---

# 11. Delete Post

Authenticated users can delete their own posts.

```text
DELETE /api/posts/{postId}
```

### Requirements

- User must be authenticated.
- User must own the post.
- Related comments and likes should also be removed or handled according to the database relationship strategy.

Successful response:

```text
204 No Content
```

---

# 12. Comments

Authenticated users can comment on blog posts.

A comment contains:

- ID
- Content
- Author
- Post
- Created date
- Updated date

Example:

```json
{
  "id": 100,
  "content": "Great article!",
  "author": {
    "id": 10,
    "name": "John Doe"
  },
  "postId": 1,
  "createdAt": "2026-08-19T11:00:00Z",
  "updatedAt": "2026-08-19T11:00:00Z"
}
```

---

# 13. Create Comment

```text
POST /api/posts/{postId}/comments
```

Request:

```json
{
  "content": "Great article!"
}
```

### Requirements

- User must be authenticated.
- Post must exist.
- Comment content cannot be empty.
- The authenticated user becomes the comment author.

---

# 14. Update Comment

Users can update their own comments.

```text
PUT /api/comments/{commentId}
```

Request:

```json
{
  "content": "Updated comment"
}
```

Users cannot update another user's comment.

---

# 15. Delete Comment

Users can delete their own comments.

```text
DELETE /api/comments/{commentId}
```

Users cannot delete another user's comment.

---

# 16. Likes

Authenticated users can like a blog post.

```text
POST /api/posts/{postId}/like
```

The system must ensure that a user can only have one active like for a particular post.

For example:

```text
User A → Post 1 → Like
```

Creating another like should not create a duplicate record.

---

# 17. Unlike Post

Users should be able to remove their like.

```text
DELETE /api/posts/{postId}/like
```

If the user has not liked the post, the operation should be handled gracefully.

---

# 18. Like Count

Each post should expose the total number of likes.

Example:

```json
{
  "id": 1,
  "title": "Introduction to System Design",
  "likeCount": 25
}
```

The system should avoid duplicate likes from the same user.

A database-level unique constraint should be used where possible:

```text
UNIQUE(user_id, post_id)
```

# 22. Validation

The API should validate all incoming data.

### User

- Name: required
- Email: required and valid
- Email: unique
- Password: required and minimum length

### Post

- Title: required
- Title: minimum/maximum length
- Content: required

### Comment

- Content: required
- Content: minimum/maximum length

Invalid requests should return:

```text
400 Bad Request
```

with a meaningful error response.

---

# 23. Error Handling

The API should use consistent error responses.

Example:

```json
{
  "status": 404,
  "message": "Post not found"
}
```

Common HTTP statuses:

| Status | Meaning                                  |
| ------ | ---------------------------------------- |
| 200    | Successful request                       |
| 201    | Resource created                         |
| 204    | Successful request with no response body |
| 400    | Invalid request                          |
| 401    | Unauthenticated                          |
| 403    | Not authorized                           |
| 404    | Resource not found                       |
| 409    | Resource conflict                        |
| 500    | Internal server error                    |

# 24. Non-Functional Requirements

### Security

- Passwords must be hashed.
- Authentication tokens must be securely generated.
- Protected endpoints must require authentication.
- Authorization must be checked at the resource level.
- Users must not be able to access or modify another user's private resources.
- Input must be validated and sanitized.

### Performance

- Post listing should support pagination.
- Database queries should avoid unnecessary N+1 queries.
- Frequently accessed relationships should be optimized when necessary.

### Maintainability

The backend should separate:

- Controllers/API layer
- Business logic/service layer
- Data access/repository layer
- Domain/models
- Authentication/authorization
- Validation
- Error handling

# 25. Acceptance Criteria

## Authentication

- [ ] A user can register with a unique email.
- [ ] A user can log in with valid credentials.
- [ ] Invalid credentials are rejected.
- [ ] Protected endpoints reject unauthenticated requests.
- [ ] Passwords are never stored as plain text.

## Posts

- [ ] Authenticated users can create posts.
- [ ] Users can retrieve a list of posts.
- [ ] Users can retrieve an individual post.
- [ ] Users can update their own posts.
- [ ] Users cannot update another user's posts.
- [ ] Users can delete their own posts.
- [ ] Users cannot delete another user's posts.
- [ ] Post listing supports pagination.

## Comments

- [ ] Authenticated users can comment on posts.
- [ ] Users can update their own comments.
- [ ] Users cannot update another user's comments.
- [ ] Users can delete their own comments.
- [ ] Users cannot delete another user's comments.
- [ ] Comments are associated with both a user and a post.

## Likes

- [ ] Authenticated users can like posts.
- [ ] Users cannot create duplicate likes.
- [ ] Users can unlike posts.
- [ ] Posts expose their like count.
- [ ] A database constraint prevents duplicate user/post likes.

# 27. MVP Definition

The first version should focus only on:

```text
Authentication
     │
     ├── Register
     └── Login
          │
          ▼
       Blog Posts
          │
          ├── Create
          ├── Read
          ├── Update
          └── Delete
          │
          ├──────────────┐
          ▼              ▼
       Comments         Likes
          │              │
          ├── Create     ├── Like
          ├── Update     └── Unlike
          └── Delete
```

The MVP is complete when users can **register → login → create posts → read posts → comment → like → edit/delete their own content**, while the system correctly enforces authentication and ownership-based authorization.
